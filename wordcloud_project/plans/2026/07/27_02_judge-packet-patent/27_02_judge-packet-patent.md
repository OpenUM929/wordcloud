## 1. 배경 및 목적

사용자는 이미 특허 1건을 출원·승인받았다 — `wordcloud_project/plans/patent.txt`(210행, 발명의 명칭: "다면평가 처리를 위한 통합 인사데이터 프레임워크 설계 방법 및 시스템"). 이 특허 위에서, 이번에 추가로 구현·운영 중인 기능 — "감정어 분석 AI가 판단하기 어려운 문장을 별도 파일로 뽑아 고급 AI(Claude)에게 판정시키고, 그 결과를 프로그램 수정 없이 그대로 시스템에 반영하는 구조" — 를 별도(추가) 특허로 출원하기 위한 **명세서 초안 준비용 계획서**를 작성한다.

기능은 이미 구현·운영 중이므로 이 계획서는 신규 구현 계획이 아니라, 기존 코드를 근거로 발명 상세·데이터 양식·청구항 스케치를 정리하는 문서 작업이다. **코드는 1행도 변경하지 않는다.**

## 2. 기존 특허(patent.txt)와의 관계 및 차별점

`D:\dev\wordcloud\wordcloud_project\plans\patent.txt`(210행, `Read`로 1~167행 직접 통독 완료)의 핵심 청구 범위는 다음과 같이 확인된다.

- §2(종래기술)~§3(1): "기본 인사데이터(Individual Evaluation HR Data)"·"통합 인사데이터(Consolidated HR Data)" 이원 구조, `evaluator_department`/`evaluator_position` 등 인사 필드 내장, `version`/`evaluation_date`를 통한 데이터 연속성, `data_integrity_hash`(SHA-256) 무결성 검증.
- §3(2) 79~112행: 기본 인사데이터 스키마에 `emotion_analysis_results: {overall_sentiment, confidence_score, sentence_level_analysis, key_emotion_words}` 필드가 정의되어 있다 — 즉 **감정분석 "결과를 저장하는 스키마"까지만** 청구 범위이며, 그 결과를 만드는 과정에서 "판단이 어려운 문장을 외부 AI에게 위임해 판정시키고, 그 판정을 프로그램 수정 없이 흡수한다"는 개념은 210행 전체 어디에도 등장하지 않는다(§3(3) 160~167행의 "구현 방법" 도입부까지 확인, 이후 §3(3) 상세 구현 단계도 데이터 입력·매핑·정제 절차이지 AI 위임 판정 절차가 아님).

따라서 이번 발명은 patent.txt의 `emotion_analysis_results` 필드에 값을 채우는 **한 방식**(외부 고급 AI에게 하드케이스만 골라 위임하고, 그 결과를 프로그램 수정 없이 흡수)에 관한 것으로, patent.txt의 청구범위와 **개념적으로 겹치지 않는 신규 구성**이다. 다만 변리사 검토 시 patent.txt를 선행기술(자기 인용)로 명시할 필요가 있다(§8 다음 단계 참조).

## 3. 발명 상세 — 코드 근거 (직접 검증 완료)

### 3.1 핵심1: AI 출력을 시스템 요구 조건에 맞춘 프롬프트 구성 수단

파일: `D:\dev\wordcloud\wordcloud_project\src\services\judgment_packet_service.py`(전체 521행 — `wc -l` 기준 521, 파일 말미 개행 없어 `Read` 도구 cat -n 표시는 522행까지 보임. 이하 라인 번호는 `Read` cat -n 기준).

- `_packet_skeleton(packet_id, source)`(97~160행) — 왕복 패킷의 골격을 생성하는 함수. 반환 dict에 다음이 포함된다.
  - `_doc`(100~105행): status 코드 의미를 문장으로 명시(`1=AI판정대기, 2=사람판정대기, 3=AI작업완료, 4=Human작업완료, 10=AI DB반영완료, 11=Human DB반영완료`) — 받는 쪽(AI)이 이 설명만 보고 처리 방법을 알 수 있게 구성.
  - `_stages.judge`(128~150행): `instruction`(130~132행) — "각 items[]의 text를 읽고 ai_reference에 {polarity, confidence, reason}을 채워라. 긍↔부 확신 시 status=3, 애매하면 status=2"라는 **AI에게 내려지는 프롬프트 본문**.
  - `_stages.judge.rules`(133~141행) — 6개 규칙이 리스트로 명시되어 있다. 실제 코드 원문 인용:
    1. `'긍↔부(긍정↔부정) 오분류 0 이 최우선 — 확신 없으면 status=2.'`
    2. `'중립↔긍정은 허용(과하게 부정으로 내리지 말 것).'`
    3. `'"보완점 없음/단점 없습니다" 등 약점없음 선언은 neutral.'`
    4. `'"~필요/요구/했으면 좋겠" 등 건설적 비판은 negative.'`
    5. `'cur_rule_label 은 현재 시스템 추정치(참고용) — 맹신 말고 문장으로 판정.'`
    6. `'model_ref 는 파인튜닝 모델의 캘리브레이션(T scaling) 신뢰도(참고용, 없을 수 있음) — confidence 가 낮은 item 은 status=2(사람) 쪽으로 보수적으로.'`
  - `_stages.judge.output_schema`(142~149행) — AI가 반드시 채워야 할 출력 스키마를 코드로 강제 명시: `ai_reference: {polarity: 'positive|negative|neutral', confidence: 'high|medium|low', reason: '짧은 근거(선택)'}`, `status: '3=확신(AI 작업완료, 이후 버튼으로 DB 반영) | 2=애매(사람 게시판)'`.
  - `select_hard_sentences(ev, db_id, existing_corr, margin=0.05)`(163~204행) — 순수 함수. 하드케이스(=KoTE argmax 극과 규칙판정 극이 불일치하거나(`is_pol`, 182행) `|pos-neg| < margin`인 저마진(`is_low`, 183행))만 골라 item 리스트를 만든다. item 필드(190~203행): `rec_id, key{db_id,sent_idx}, text, field, cur_rule_label, kote, gap, hard, margin_band, ai_reference, status, human_decision` — 이것이 AI에게 실제로 전달되는 입력 데이터 레코드 형식이다.
  - `build_judgment_packet(batch_id=None, margin=None, limit=None)`(263~294행) — `_packet_skeleton` + `select_hard_sentences`를 합쳐 실제 패킷 dict를 생성하고 반환(`packet, quarantined`).

이 4개 요소(status 의미 설명, judge 단계 instruction, 6개 규칙, output_schema)가 결합되어, **AI가 별도 대화나 예시 없이도 패킷 파일 하나만 읽으면 시스템이 요구하는 조건(스키마·판정규칙)에 정확히 부합하는 출력을 생성하도록 구성된 프롬프트**다. 이것이 핵심1의 구성수단이다.

### 3.2 핵심2: 프로그램 수정 없는 AI 산출물 무흡수(無修正 統合) 효과

핵심2의 근거는 "AI가 채운 결과(status=3, 승인 대기)"와 "사람이 채운 결과(status=4, 승인 대기)"를 **DB에 반영하는 코드 경로가 분기 없이 동일하다**는 사실이다. 아래는 실제 코드를 직접 재확인한 결과다.

- `_final_label(it)`(317~326행) — item의 최종 라벨을 정하는 함수. 실제 코드:
  ```python
  def _final_label(it):
      hd = it.get('human_decision')
      if hd in _VALID_LABELS:
          return hd
      pol = (it.get('ai_reference') or {}).get('polarity')
      if pol in _VALID_LABELS:
          return pol
      res_label = (it.get('result') or {}).get('label')
      return res_label if res_label in _VALID_LABELS else None
  ```
  → `human_decision`이 있으면 그 값을, 없으면 `ai_reference.polarity`를 그대로 반환한다. **AI 판정과 사람 판정을 구분하는 `if 주체==AI: ... else: ...` 같은 분기가 아니라, "필드 우선순위"로만 처리**된다.
- `resolve_item(it)`(350~358행) — `_map_status(it)`로 status를 정규화하고, 라벨 보유 상태(3/4/10/11)면 `(status, _final_label(it))`를 반환하는 순수 함수. AI 결과든 사람 결과든 동일한 이 함수 하나를 통과한다.
- `_merge_corrections_by_db(conn, by_db)`(361~383행) — `{db_id: {sent_idx: label}}`를 `evaluations.sentiment_corrections`에 in-place 병합하는 함수. 실제 코드에 `label`의 출처(AI인지 사람인지)를 확인하는 조건문이 전혀 없다 — 그냥 `{**existing, **sent_corr}`(377행)로 병합한 뒤 `UPDATE evaluations SET sentiment_corrections = ?`(378~380행) 한 줄로 기록한다.
- `apply_judgment_packet(packet, conn=None)`(386~439행) — 각 item에 대해 `resolve_item(it)`를 호출(401행)하고, status가 10/11(DB 반영 완료)인 것만 `by_db`에 쌓아(424행) 마지막에 `_merge_corrections_by_db`를 1회 호출(426행)한다. AI(3→10)든 Human(4→11)이든 **동일한 `by_db.setdefault(...)[str(sent_idx)] = label`(424행) 한 줄로 수렴**한다.
- `apply_db_to_packet(packet, conn=None, target='all')`(442~482행) — "DB에 반영" 버튼 처리 함수. `want` 딕셔너리(452~453행)로 대상 status만 필터링(`target='ai'`→{3}, `'human'`→{4}, `'all'`→{3,4})하지만, 필터링 이후 라벨을 뽑아 `by_db`에 넣는 로직(456~468행)과 최종 DB 반영 호출(`_merge_corrections_by_db(conn, by_db)`, 476행)은 AI/Human 구분 없이 **동일 코드 1벌**이다. 차이는 오직 `it['status']`를 10(469~471행) 또는 11(472~474행)로 바꾸는 사후 마킹뿐이며, 이는 감사(audit) 목적의 상태 전이이지 별도 파싱·통합 로직이 아니다.

**결론(직접 검증)**: AI가 채운 패킷(`status=3`, `ai_reference.polarity`)과 사람이 채운 패킷(`status=4`, `human_decision`, `update_packet_decisions()`(494~521행)가 세팅)은 시스템에 반영되는 시점에 **완전히 동일한 함수 경로(`resolve_item → _merge_corrections_by_db`)를 통과**하며, 코드베이스 어디에도 "AI 결과 파싱 코드"와 "사람 결과 파싱 코드"가 별도로 존재하지 않는다. 이는 핵심1(프롬프트가 AI 출력 스키마를 사람 판정 스키마와 동형(同形)으로 강제)이 있기 때문에 가능한 구조다 — 즉 **핵심1이 핵심2를 가능케 하는 구성요소** 관계가 코드로 실증된다.

- **문서 리스크 2 — 청구항 스케치의 법적 미확정**: §7의 청구항은 기술 구성 요약이며 특허법상 요건(신규성·진보성·명확성) 검토 전이다. **반드시 변리사 확인 필요**. 2026-07-27 개정으로 (a) 효과-인과 연결 문구 추가(명확성 보강), (b) "사람"을 웹 기반 검토 인터페이스로 치환(카테고리화 리스크 완화)했으나, 두 개정 모두 **완전한 해소가 아닌 완화 조치**이며 실제 등록 가능 여부는 변리사가 최종 판단해야 한다. 병행 시스템(장치) 청구항 준비도 §7 하단에 논의 항목으로 남겨둠.
- **문서 리스크 4 — 데이터 구조/기록매체 청구항(독립항6)의 "정보의 단순한 제시" 해당 위험**: 특허청 심사기준상 데이터 구조 청구항은 그 구조가 "컴퓨터가 수행하는 처리 내용을 특정"할 때만 발명으로 인정되고, 단순히 데이터의 내용·서식만을 청구하면 "정보의 단순한 제시"로 거절된다. §7 독립항6은 입력 템플릿·출력 템플릿·상태 코드 필드가 실제 처리 분기를 결정한다는 §3.2 코드 근거를 바탕으로 작성했으나, 이 구분선이 실제 심사에서 어느 쪽으로 판단될지는 **변리사 확인이 반드시 필요**하다.
- **문서 리스크 3 — 코드 변경 이력 추적**: `judgment_packet_service.py`는 2026-06-24(`feat: judgment packet & acquired handoff services + UI`) 최초 커밋 이후 2026-07-09에 "용어변경 전 스냅샷" 커밋이 있었다(`git log --follow` 결과). 명세서 작성(6단계, 향후) 시 최신 커밋 기준으로 라인 번호를 다시 확인해야 한다(라인 번호는 코드 변경에 따라 이동 가능).
