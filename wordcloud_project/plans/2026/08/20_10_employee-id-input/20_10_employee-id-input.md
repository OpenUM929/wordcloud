## 1. 배경 및 목적

그룹분석 화면에서 대상 직원을 고를 때 약 1.9만 명(DL-3) 규모의 드롭다운을 스크롤/검색해야 해 불편하다. 사번을 직접 입력해 바로 찾을 수 있게 해 조작을 간소화한다.

## 2. 현재 시스템 분석

- **현재 마크업**: `<select id="employeeSelect"><option value="">로딩...</option></select>`(`wordcloud_project/web/templates/perspective_test.html:252`).
- **채우는 코드**: `loadMeta()`(540~558행)가 `_meta.employees`를 순회해 `option.value = e.employee_id`, `option.textContent = "${label} (${dept}) ${evaluation_count}건"`으로 채움.
- **`.value`를 읽는 지점 전수(13곳, `grep -n "employeeSelect" perspective_test.html` 실측)**: 717(`toggleAllEmployees`의 `disabled` 제어), 960·1280·1457·1461(진행 중 `disabled` on/off), 1042(`saveDeploy` 이전 버전 참조 — 실제로는 매트릭스 생성 함수), 1319·1381·1431·1462(페이지 상태 저장/복원 `params.empId`), 1515(`saveDeploy`), 1875(`saveGraph`), 3852(`change` 이벤트 리스너 → `_autoSavePageState`). **이 전부가 `.value`를 "사번 문자열"로 취급**한다 — 요구사항 원자화 1.3의 결론(입력값=사번 유지)이 이 13곳을 그대로 두고 UI만 바꿀 수 있는 전제.
- **검색 API 존재 여부**: 이번 조사에서 "직원 검색"(사번/이름 부분일치, 페이지네이션) 전용 엔드포인트를 찾지 못했다 — `GET /api/perspective/meta`는 항상 전체 목록을 반환하는 구조(§20_09)라, 요구사항 원자화 1.2를 "타이핑마다 서버 검색"으로 가면 **신규 엔드포인트가 필요**하다.

## 3. 구현 상세

### 3.1 백엔드

- 신규 엔드포인트 `GET /api/perspective/employees/search?q=<사번 또는 이름 일부>&limit=20` 추가(정확한 경로명은 착수 시 기존 네이밍 컨벤션 재확인).
- 구현은 `get_matrix_meta_light()`(`perspective_service.py:2843`)의 `emp_rows` 쿼리(2883~2888행)를 참고하되, 전체를 가져오지 않고 `WHERE e.employee_id LIKE ? OR e.name LIKE ?` + `LIMIT`을 추가한 경량 쿼리로 신규 함수(가칭 `search_employees(query, limit=20)`)를 만든다. **가명 역변환은 검색 결과(최대 `limit`건)에만 적용** — 20_09가 지적한 "전 직원 4회 역변환" 비용이 검색형으로 가면 사실상 사라진다(관리자 검색 1회당 최대 `limit`명만 역변환).
- `_is_admin()` 가드는 기존 `/meta`와 동일하게 유지.

### 3.2 프론트엔드

- `<select id="employeeSelect">`를 `<input id="employeeIdInput" list="employeeDatalist">` + `<datalist id="employeeDatalist">` 또는 자체 드롭다운 제안 UI(브라우저 datalist는 커스텀 스타일이 제한적이므로, 기존 UI 톤과 맞추려면 자체 구현이 나을 수 있음 — 착수 시 UI 톤 비교 후 결정)로 교체.
- 입력 시(디바운스 300ms 권장, 코드베이스에 이미 있는 디바운스 패턴 — `perspective_test.html:3838` 배치 명칭 입력의 `_batchTitleTimer` 참고) 3.1의 검색 API를 호출해 후보를 보여주고, 선택 시 `employeeIdInput.value`를 사번으로 고정(요구사항 원자화 1.3), 이름/부서는 입력창 옆 `<span>`에 별도 표시.
- §2에서 나열한 13곳의 `document.getElementById('employeeSelect').value`를 **모두** `document.getElementById('employeeIdInput').value`로 일괄 치환(요소 id 변경에 따른 기계적 치환 — 로직 변경 없음, 13곳 전부 빠짐없이 확인 필요).
- `toggleAllEmployees()`(717행)·진행 중 `disabled` 처리(960·1280·1457·1461행)는 `<input>`의 `disabled` 속성으로 동일하게 동작(`<select>`와 API 동일).

## 7. 리스크 및 제약

- 자유 텍스트 입력으로 바뀌면서 "목록에 없는 값은 선택 자체가 불가능"했던 기존 안전장치가 사라짐 — **구현 결정**: 입력 자체는 막지 않는다(사번 직접 입력이 목적이므로). 제안에서 고르면 입력창 아래에 `이름 (부서) N건`이 초록색으로 뜨고, 없는 사번이면 제안 목록이 "일치하는 직원이 없습니다"로 뜬다. 그래도 실행하면 기존 서버 응답(`'<사번>' 직원의 조건에 맞는 평가가 없습니다`)이 그대로 안내된다 — 차단 대신 두 단계 피드백.
- 13곳 치환 중 하나라도 누락되면 그 지점만 조용히 깨질 수 있음(예: 저장은 되는데 페이지 복원만 안 되는 식) — 구현 후 §6 체크리스트 전항목 확인 필수.
- 검색 엔드포인트가 신규이므로 `_is_admin()` 가드 등 기존 `/meta`의 보안 전제를 빠짐없이 옮겨야 함.
