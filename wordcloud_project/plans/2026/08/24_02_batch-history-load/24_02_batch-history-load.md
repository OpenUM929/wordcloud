**`loadBatchHistory()`** (`:3877-3926`):

- 렌더 후 `_updateBatchScopeSummary()`(`:3928-3932`) 호출.

**`onBatchScopeChange()`** (`:3940-3951`):
```js
function onBatchScopeChange() {
    const boxes = document.querySelectorAll('.batchScopeCheckbox:checked');
    _selectedBatchIds = Array.from(boxes).map(cb => cb.value);
    _updateBatchScopeSummary();
    // 13_05 §8-1: 디바운스 타이머 시작 시점에 스피너를 켜고, loadMeta() 완료(성공/실패 무관)에 끈다.
    _showBatchScopeLoading(true);
    // D-4: 다다닥 체크할 때 요청이 겹치지 않도록 디바운스(300ms) 후 재조회
    if (_batchScopeDebounceTimer) clearTimeout(_batchScopeDebounceTimer);
    _batchScopeDebounceTimer = setTimeout(() => {
        loadMeta().finally(() => _showBatchScopeLoading(false));
    }, 300);

```

### 2.2 병행 진행 중인 캐시 작업 — 실측 결과 (코드에 아직 없음)

이 계획서가 전제하는 "대상 직원 메타 데이터 클라이언트 캐싱"(배치 범위를 키로 하는 `Map`)은 그룹 지시문에 따르면 다른 ui-builder 작업으로 **병행 구현 중**이다. `git diff -- wordcloud_project/web/templates/perspective_test.html`(2026-08-24 작업 트리, 297줄 추가·19줄 삭제)을 전수 확인한 결과, 이 diff는 ①직원 콤보박스 복원(20_10) ②그래프 "전체 선택"(12_01 §11-2) ③배치 ID 편집 모달(20_07) 관련 변경만 포함하며 **`Map` 기반 캐시·`_metaCache` 류의 코드는 아직 어디에도 없다**(실측, 예측 아님). 즉 이 계획서 작성 시점 기준 캐시는 코드가 아니라 **병행 진행 중인 별도 작업의 산출물로만 존재**한다.

따라서 이 계획서는 캐시의 **정확한 변수명·키 직렬화 방식(예: 정렬된 `batch_ids` 배열의 `JSON.stringify` 또는 `join(',')`)·무효화 호출 지점**을 알지 못한 채 인터페이스 수준으로만 설계한다. 아래 §5의 `_isBatchScopeCached(ids)` 같은 함수명은 **가칭**이며, 구현 착수 시 실제 캐시 작업의 커밋을 먼저 확인하고 그 캐시가 노출하는 실제 API(`has`/`get`/무효화 콜백)에 맞춰 이름·시그니처를 조정해야 한다(§9 R-1).

| 3 | **초기 체크박스 미선택 상태에서의 사용자 혼동** | 진입 시 `_selectedBatchIds = []`(전체 배치)이며 `window.onload = loadMeta`(`:567`)가 이 상태를 이미 1회 로드한다. 그러나 현재 화면에는 이 "전체 범위가 이미 로드됨"을 알려주는 표시가 전혀 없다 — 사용자가 아무것도 체크하지 않은 채 로드 버튼을 찾다가 "왜 눌러야 할 게 안 보이지"라고 느낄 수 있음 | 배지 로직이 **빈 배열(전체 범위)도 하나의 캐시 키로 취급**해 최초 진입 시 "✅ 전체 배치 로드됨" 배지를 항상 표시(§5.3). 로드 버튼은 미체크 상태에서 기본 비활성화 + "현재 전체 배치가 이미 반영되어 있습니다" 안내로 혼동을 제거 |
| 4 | **재클릭 시 버벅임** | 캐시가 없어 A만 체크→A,B 체크→다시 A만 체크처럼 조합을 오갈 때마다 매번 재조회(체감 지연) | 이미 조회했던 조합(A 단독, A+B 조합)은 캐시에 남아 있으므로 같은 조합으로 돌아오면 로드 버튼을 눌러도 **네트워크 요청 없이 즉시** 반영 — 단, 배치 생성/삭제/명칭·ID 변경 시 캐시가 전체 무효화되므로 그 사이 재클릭은 여전히 재조회됨(§9 R-1) |
| 5 | **배치별 병렬 로드 여부** | 없음(현재는 체크된 조합 전체를 1회 요청으로 처리) | 로드 버튼은 **현재 체크된 조합을 단일 요청 1회**로 처리하는 것을 기본 설계로 한다(§4 D-2). 캐시 키가 "조합" 단위이므로 배치를 하나씩 쪼개 병렬 요청하면 캐시 재사용 이득이 사라지고 서버 왕복 수만 늘어난다 — 단, 배치 단위 개별 로드 버튼이 실제로 필요한지는 확정하지 않고 **확인 필요(§10)** 로 남긴다 |

## 5. 구현 상세 (D-1~D-4 확정 후 착수)

> 아래는 D-1을 (A) 조합 단위로, D-2를 (A) 단일 로드 버튼으로, D-3을 (A) 로드=자동 반영으로 가정했을 때의 **기준 설계**다. 사용자가 §10에서 다른 안을 택하면 5.2(배지 렌더)·5.4(로드 버튼 핸들러)만 그 안대로 바뀌고 나머지(5.1 상태 분리, 5.3 초기 상태 처리)는 공통이다.

### 5.1 상태 분리 — 자동 재조회 폐지

`onBatchScopeChange()`(`:3940-3951`)를 다음 두 함수로 분리한다(기존 함수명 유지, 신규 함수는 가칭):

- `onBatchScopeChange()` — 체크박스 목록 → `_selectedBatchIds` 갱신, `_updateBatchScopeSummary()` 호출, **신규** `_renderBatchLoadBadge()`(가칭, §5.3) 호출. `loadMeta()` 호출·디바운스 타이머·`_showBatchScopeLoading()` 호출을 **제거**한다(자동 재조회 폐지, 요구사항 1·4).
- `applyBatchScope()`(가칭, 신규) — "로드" 버튼의 `onclick` 핸들러. 캐시 히트 시 캐시값을 즉시 사용해 D-3(A)이면 화면 반영까지 수행, 캐시 미스 시 `_showBatchScopeLoading(true)` → `loadMeta()` → `.finally(() => _showBatchScopeLoading(false))`(기존 13_05 §8-1 스피너 패턴 재사용).

`_batchScopeDebounceTimer` 변수(`:556`)는 더 이상 필요 없어지므로 제거 대상(단, 다른 곳에서 참조 여부는 구현 착수 시 재확인 — 실측상 `onBatchScopeChange()` 1곳만 사용).

### 5.2 배지 UI — `loadBatchHistory()`(`:3877-3926`) 수정

표 헤더(`:3903`)에 "상태" 컬럼 1개 추가. D-1(A) 조합 단위 기준으로는 배치별 행 배지 대신 **패널 헤더 요약 영역**(`batchScopeSummary` 옆, `:386-387`)에 단일 배지를 둔다("✅ 이 조합 로드됨" / "⏳ 로드 필요 — [로드] 버튼을 누르세요"). D-1(B) 개별 배치 단위가 채택되면 `:3904-3917`의 행 템플릿 리터럴에 배지 `<td>`를 추가하는 구조로 바뀐다(이 경우 §4 D-1 표에 정리한 판정 정확도 트레이드오프를 감수해야 함).

### 5.3 초기 상태(문제 3) 처리

`window.onload = loadMeta;`(`:567`)로 전체 범위가 항상 1회 로드되므로, 페이지 진입 직후 `loadBatchHistory()`가 실행되는 시점(`window.addEventListener('load', ...)`, `:4090-4093`, 500ms 지연)에 "전체 배치 = 이미 로드됨" 배지를 초기값으로 세팅한다. 체크박스가 하나도 없는 상태(`_selectedBatchIds.length === 0`)에서는 로드 버튼을 `disabled`로 두고, 버튼 근처에 "체크 없음 = 전체 배치(이미 로드됨)" 문구를 표시해 "눌러야 할 버튼이 안 보인다"는 혼동을 없앤다(§3 문제3 대응).

### 5.4 새 버튼 마크업

`:388-390`의 버튼 그룹(`<span style="margin-left:auto;display:flex;gap:4px;">`)에 새로고침 버튼 옆으로 로드 버튼을 추가:

위 6항목은 서버 기동이 필요한 실동작 검증이며, 사용자 승인 후 **사용자가 직접 서버를 기동**한 상태에서 수행한다(DL-12 — 에이전트가 임의로 서버를 실행하지 않음). 통과 전에는 상태를 `Done`으로 올리지 않는다(DL-10).

## 10. 확인 필요 — 사용자 확정 (2026-08-24)

사용자 지시(원문): "체크박스를 선택할때는 아무 동작을 안한다. 선택된 배치 로드 라는 버튼을 만들고 이것을 누르면 해당 배치 값들을 가져오고 로드됨으로 표시한다."

1. **로드 버튼 범위 → D-2 안 (A) 확정**: "선택된 배치 로드" 버튼 1개, 체크된 조합 전체를 한 번에 반영. 배치 단위 개별 로드 버튼 불필요.
2. **배지 판정 단위 → D-1 안 (A) 확정**: 체크된 조합 단위로 "로드됨" 표시("해당 배치 값들을 가져오고 로드됨으로 표시" = 버튼으로 가져온 그 조합에 대한 표시). 캐시 키(조합 단위)와 정확히 일치, R-2(개별 배지 오판 리스크) 해당 없음.
3. **로드 후 자동 반영 → D-3 안 (A) 확정**: 버튼 클릭이 곧 데이터 가져오기+화면 반영("값들을 가져오고 로드됨으로 표시"). 별도 "적용" 액션 불필요.
4. **전환 안내 문구 → 안 (A) 채택**: 사용자가 명시적으로 답하지 않았으나 잠정 권장안(A)을 그대로 채택 — "체크 후 [선택된 배치 로드] 버튼을 눌러야 반영됩니다" 안내를 패널에 추가(저위험, 기존 자동 동작 습관과의 충돌 방지).

R-1(병행 캐싱 의존)은 해소됨 — `_metaCache`(Map)·`_metaCacheKey()`가 이미 `perspective_test.html:575-579`에 구현되어 있음(2026-08-24 같은 세션에서 병합 완료, git 커밋 전 워킹트리 확인).
